# ADR 0002：M0b 注入機制與單次預算語意

狀態：已接受（2026-09-04）
關聯：SPEC §17.3、§17.4-4、§17.6、§17.7、§19、§22 M0b；ADR 0001（M0a hardening）
標記：§23-9 ASK——決策一（注入機制替代 §17.4-4 字面 `docker cp`）屬 spec 未
覆蓋的決策點，本文列出選項與理由供確認；決策三（本地映像 digest 重錄流程）
的 `/doctor` 行為屬 M0d 實作時同樣需要確認的範圍。

## 決策一：witness／payload 注入改走 per-run named volume

### 問題

SPEC §17.4-4（SPEC.md:781）規定啟動序為 `docker create` → `docker cp` witness 檔案
（`/aegis/witness/`）與 payload（`/aegis/payload.txt`）→ `docker start`。
但 §17.1 同時要求 run 容器 `--read-only`。docker 29 實測：

- `docker cp` 對 `--read-only` 容器的 rootfs／tmpfs 路徑一律回
  `container rootfs is marked read-only`（daemon 層硬限制，無 flag 可繞）；
- 唯一可寫的是 **named volume 掛載點內**的路徑（與 `/aegis/out` 同機制）。

兩條規定在 docker 29 互相矛盾，必須擇一機制替代。

### 決策

注入機制改為 per-run named volume（`internal/sandbox/stage.go`）：

1. `docker volume create aegis-witness-<runID>`；
2. staging 容器（`docker create`，helper 映像、不啟動、帶 `aegis.run_id` label）
   掛該 volume，witness 檔案與 `payload.txt` 以 tar 經 stdin `docker cp -` 注入，
   隨即刪除 staging 容器；
3. run 容器：
   - `-v aegis-witness-<runID>:/aegis/witness:ro`（witness 目錄唯讀）；
   - `--mount type=volume,src=aegis-witness-<runID>,dst=/aegis/payload.txt,
     volume-subpath=payload.txt,readonly`（**契約路徑 `/aegis/payload.txt` 不變**，
     docker ≥25 的 volume-subpath 單檔掛載，本機 docker 29.4.3 實測可用）；
4. reclaim 時 witness volume 與 out volume 一併刪除；失敗路徑由
   Reaper(runID)（staging 容器）＋ RemoveWitnessVolume best-effort 清收。

### 備選與否決理由

| 備選 | 否決理由 |
| --- | --- |
| host 可寫 bind mount | 直接違反 §17.6「禁止任何 host 目錄以可寫模式掛入證明 run 容器」 |
| 映像 bake witness | 每 run 內容不同，違反映像 build/run 分離（§7.1）且映像只能以 digest 引用 |
| payload 改走環境變數 | 偏離 §17.4 契約路徑；env 屬 policy 決定的 service 接線，不收模型輸入 |
| volume-subpath 掛 payload＋witness 目錄（本決策） | 契約路徑完全不變；witness 對容器唯讀；與 /aegis/out 同為 named volume 機制 |

### 安全性等價分析

- 注入仍全為檔案、無 host 可寫 bind mount（§17.4-4 精神不變）；
- witness 目錄與 payload 檔案對 run 容器**唯讀**——比原 cp 進 rootfs 更緊
  （witness 無法改寫自身或 payload）；
- staging 容器不啟動、僅掛該 volume、digest-pinned helper 映像；
- tar entry 一律 mode 0644、root 擁有，容器內 non-root（65532）可讀不可寫。

### 遺留行為

- `docker volume rm` 在容器剛刪除後有釋放競態（"volume is in use"），
  `removeVolumeRetry` 以 3 次×1s 重試吸收。

## 決策二：M0b 決定性 harness 的單次預算語意

§19 決策樹的預算語意為 agent 迴圈（M0c）設計：env／harness／hypothesis 各有
重試預算。M0b 的 deterministic harness 無自我修正能力（無 LLM 出新假設），
呼叫端以 `Budget{MaxEnv:1, MaxHarness:1, MaxHypotheses:1}` 驅動，任一失敗即終態：

- 執行層錯誤（docker／reclaim）→ `ENV_ERROR`；
- harness 控制點失敗（negative 誤觸發、positive 未命中）→ `NOT_PROVEN`
  （reason `harness_budget`）；
- exploit 未命中（positive 已通過、控制點證明 harness 是通的）→
  `HYPOTHESIS_REJECTED`。

這是誠實邊界而非缺陷：M0b 的職責是把「證明機器本身」驗到可運作；重試與
多假設迭代屬 M0c agent 迴圈（§9.3、§18.2 回饋協定），屆時預算由 aegis.toml
驅動。

## 決策四：trace shim 以 connect factory 子類別觀測（Python 3.12）

Python 3.12 的 `sqlite3.Cursor`／`Connection` 為不可變 C 型別，對其 setattr
一律 `TypeError: cannot set 'execute' attribute of immutable type`（實測），
原 §17.3「monkeypatch sqlite3 的 execute 路徑」字面機制不可行。改以等價觀測面：

- `sqlite3.connect` 改回傳 `TracedConnection(sqlite3.Connection)` factory，
  其 `cursor()`／`execute()`／`executemany()` 一律回 `TracedCursor`
  （`sqlite3.Cursor` 可被子類別化，官方支援的 cursor_factory 機制）；
- trace entry 欄位閉集 `{ts, sql, params, error, rows}` 與 §17.3 完全一致；
- `check_same_thread=False` 由 shim 的 connect wrapper 統一提供——Flask 開發
  伺服器多執行緒派發，目標 repo 的 connect 呼叫不可修改，屬 witness 接線
  （wiring），不改變 SQL 語意與 oracle 判定；
- shim 檔案鎖寫入（多執行緒 append 安全），例外一律吞掉不改變被觀測程式行為。

## 決策五：positive 控制點未命中 → NOT_PROVEN（harness），非 HYPOTHESIS_REJECTED

§17.7 語意：**正對照通過後的 miss 才能計為反證**。SQLi 家族的 paired touch rule
（`nonce_in_field: sql`）驗證「輸入確實流進 SQL 文字」。若 witness 以參數化查詢
執行（nonce 只進 params、不進 SQL 文字），positive 控制點未命中——此時 exploit
的 miss 不可信，終態為 `NOT_PROVEN`（reason `harness_budget`），**不是**
`HYPOTHESIS_REJECTED`；三控制 run 在 positive 失敗處止步（exploit 不執行，
§5.2-3 guardrail）。

`HYPOTHESIS_REJECTED` 只出現在：positive 已通過、exploit 未命中（例：payload
無引號、流進 SQL 但不觸發 error）→ controlled_miss，唯一假設被否證。偽造
stdout 測試（§22 M0b）斷言的是「絕不 PROVEN」，其終態依控制點事實決定。

## 決策三：本地構建映像的 digest 定址

pack manifest 的 `templates[].image` 只接受 digest 形式（§7.1）。本地構建的
映像（buildkit containerd store）僅能以 **repo digest**（`RepoDigests`）定址，
image ID 不能作為 `name@sha256:` 引用（"invalid reference format"／pull denied）。
且每次 `docker build`（即使全快取命中）都會產生新的 manifest digest（config
時間戳變動）。因此：

- e2e 僅在 tag **整個不存在**時才構建；digest 不符時以 `/doctor` 語意
  要求重錄（skip 而非誤報）；
- 構建命令固定為 pack 根目錄下 `docker build -f image/Dockerfile -t <tag> .`
  （context 須為 pack 根，模板路徑才解析得到）；
- `/doctor`（M0d）需提供「重建映像 → 重錄 repo digest 進 manifest」流程。
