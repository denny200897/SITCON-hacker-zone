### F003 [P1] M0c「env 用盡 → ENV_ERROR」測試為套套邏輯：policy compiler 拒收的 spec 被誤分類為 env 並耗 env 預算
SPEC：SPEC.md §22 M0c 行 1009「env 用盡 → ENV_ERROR」＋§9.3/§19 失敗分類｜維度：acceptance-audit（R2）

agent_prover.go:250-267 把 *任何* Prove 回傳的 error 一律歸 FailureEnv（註解寫「docker 不可用等」，但程式沒有區分）。runOne（prove.go:190-192）在 policy.Compile 被拒時回 `orchestrator: policy compile: …` error，而迴圈級閘 (b)（agent_prover.go:392-411）只驗 schema／nonce placeholder／duplicate hash／preamble——schema（witness_spec.schema.json）只檢查 target_symbol 為 string，不看存在性。反例：prover 連續提交 5 個 schema 合法、payload 含 {{NONCE}}、hash 互異、但 target_symbol 為 `app.NoSuchClass.method` 的 spec：閘全數放行 → Prove → ASTCheck 失敗 → SpecError → 每次扣 env 計數；預設 MaxEnv=5 下終態 ENV_ERROR——模型造成的 spec 錯誤被記成環境故障、耗掉真正環境問題所需的預算，且這些 spec 在 journal 完全沒有 witness_spec_rejected 事件（runOne 只在 compile 成功後才 append witness_spec_submitted）。同樣適用於 unknown oracle_id、spec 內含金鑰（ReasonSecretInSpec）、generated_files 超量等 §17.9 拒收。§22 M0c「env 用盡 → ENV_ERROR」的對應測試 TestAgentProverEnvExhausted 餵的是兩次泛用 errors.New("docker unavailable")，與「所有 error→env」的實作互為套套邏輯——它驗證的是計數，不是分類邊界；宣稱的分類語意（env＝環境故障）並未被任何測試釘住。

> 證據：internal/orchestrator/prove.go:122 `if err != nil { return nil, err }`（runOne compile 錯誤向上拋）；prove.go:190-192 `if cerr != nil { return nil, budget.Verdict{}, nil, fmt.Errorf("orchestrator: policy compile: %w", cerr) }`；internal/orchestrator/agent_prover.go:250-255 `if perr != nil { rec.Verification = …NotRun; rec.FailureClass = string(domain.FailureEnv); rec.Note = "prove_error: " + … }`；internal/orchestrator/agent_prover_test.go:139 `prove := &fakeProve{errs: []error{errors.New("docker unavailable"), errors.New("docker unavailable")}}`（唯測資料也是泛用 error，故測試無法區分「分類正確」與「分類恆真」）。

**建議修法**：在 agent_prover.go 的 perr 分支先用 errors.As 解出 *policy.SpecError：命中時走 spec 拒收路徑（append witness_spec_rejected 事件含 §17.9 reason、以 operator 回饋告知具體拒收原因要求重送、不扣 env 計數），僅非 SpecError 的錯誤才歸 FailureEnv；並補一個測試：提交 schema 合法但 target_symbol 無法 AST 解析（及 unknown oracle_id）的 spec，斷言 witness_spec_rejected 落檔且 env 計數不減、迴圈續跑。

### F004 [P1] 沙箱時數上限量測的是整個 prover 迴圈 wall-clock（含 LLM 等待），慢模型會在沒跑幾次沙箱時被誤判 sandbox_budget
SPEC：§9.3（沙箱時數上限，預設每 finding 10 分鐘→NOT_PROVEN(sandbox_budget)）｜維度：agent-llm（R1）

sandboxStart 在迴圈開頭取一次、永不重置；每輪 session（含多個 LLM turn）之間才檢查 `SandboxExceeded`。SPEC 語意是『沙箱時數上限（防 hang，預設每 finding 10 分鐘）』——防的是容器 hang，不是 LLM 延遲。實際反例：prover 以 xhigh effort，單一 tool turn 常見數分鐘；3–4 個 turn（可能尚未跑任何 Prove，或只跑過一輪 3×60s 的 run）即累積 >600s，迴圈在下一輪開頭回 NOT_PROVEN（原因 sandbox_budget），attempt 記 FailureHarness＋Note sandbox_budget，終因完全與沙箱用量無關。反向漏洞：真正的 hang 發生在單次 Prove 內部時，本檢查只在 iteration 邊界生效，無法中止進行中的 Prove（僅靠 sandbox/flags.go:87 每 run 60s host timeout 兜底，與本計數器無關）。正確做法應累計各 run 的沙箱執行時長（RunRecord 有時長資訊可取），而非把 LLM 等待時間記在沙箱帳上。

> 證據：internal/orchestrator/agent_prover.go:125 `sandboxStart := time.Now()`；agent_prover.go:148-155 `counters.SandboxSecUsed = int(time.Since(sandboxStart).Seconds()); if ap.Budget.SandboxExceeded(counters) { ... return ap.terminal(domain.VerificationNotProven, domain.NotProvenSandboxBudget, ...)`（在 runtime.Run／Prove 呼叫之前判定，計時包含所有 LLM 往返）；internal/orchestrator/budget/budget.go:200-205。

**建議修法**：把計時改為沙箱實際執行時長累計：在 ap.Prove 呼叫前後取差值（或彙整 RunRecord 的各 run 時長）累加進 counters.SandboxSecUsed，並在每次 Prove 後檢查 SandboxExceeded；迴圈開頭的 wall-clock 檢查移除。Note/classification 改為 env-adjacent 或正確的 harness 語意。

### F030 [P1] §17.3 仍以「monkeypatch sqlite3」為規範機制，ADR 0002 已證不可行、ADR 0004/0005 已判定同容器 shim 不可作 trusted observer

### F109 [P2] 正式 prove 路徑不寫 verification_updated：verification 終態只存在 findings.json，journal 無法重放
SPEC：§4（狀態持久化／journal 記錄所有狀態轉移）、§21.3｜維度：state-machine（R2）

SPEC §4 要求 journal「記錄所有狀態轉移與 artifact」、§21.3 定義 verification_updated 事件正是為此。但正式 prove 路徑（cmd/aegis/main.go 444-461）拿到 ProveResult 後直接改 findings.json 的 verification/evidence_id/confidence 並寫回，從未呼叫 j.Append("verification_updated", …)；全 repo 唯一寫此事件的點是 agent_prover.go:380（未接生產路徑）。後果：(1) journal replay 無法重建任一 finding 的 verification 終態——run_completed/evidence_written 只有 exit code，分不出 PROVEN／HYPOTHESIS_REJECTED／NOT_PROVEN 的歸類；(2) report 子命令（main.go:288-347）也只讀 findings.json、完全不讀 journal，journal 對 verification/disposition 是 write-only 裝飾，§8「狀態可續跑」在 journal 側無資料可續；(3) prove 階段也沒有任何 run_started／stage_completed 事件，journal 缺整個 Stage 3/4 的階段書擋。反例：prove F-0007 得 PROVEN 後 process 被殺，journal 只有 run_completed(exit=0)+evidence_written，重放者無法得知該 finding 曾被判定 PROVEN。

> 證據：cmd/aegis/main.go:444-461：`res, err := p.Prove(...)` 之後僅 `finding["verification"] = string(res.Verification)` → `reporting.WriteFindings(runDir, findings)`，中間無任何 j.Append("verification_updated")；grep 全 repo 僅 agent_prover.go:380 一處寫此事件型別。

**建議修法**：在 main.go prove 分支拿到 ProveResult 後、寫 findings.json 前，以 j.Append("verification_updated", findingID, {verification, reason, failure_class, evidence_id}) 落事件，並補 run_started（stage=prove）／stage_completed 書擋；或把 prove 正式路徑改走 AgentProver/terminal（其已實作 journalVerification）。同時讓 report 子命令在 findings.json 之後以 journal 事件交叉驗證一致性。

### F110 [P2] duplicate-spec 閘在核可時即記 hash，env 失敗後不得重送同一 spec，擋死 §19-1 的「不改動程式、修正環境後重跑」
SPEC：§19 第 1 點（env：不改動程式，修正環境後重跑）vs §18.2／§17.9-7（同內容 hash 拒收）｜維度：state-machine（R2）

閘在核可當下就把 specHash 記入 seenHashes（agent_prover.go:138），而非在該 spec 產生 run 結果之後。§19 第 1 點明文：env 分類「不改動程式，修正環境後重跑」——此時正確動作是重送同一 spec。但 env 失敗後迴圈只送 operatorError，下一輪模型若重送同一 spec，checkSpec（agent_prover.go:403-406）以 duplicate_spec 拒收，回饋文字「同款重試不計也不收（§9.3）」把 §9.3 對「假設」的規則誤植到 env 重試上。反例：docker daemon 重啟導致一次 env 失敗後，模型唯一合法路徑是改動 payload（或任意欄位）來繞過 hash 閘——嘗試日誌裡出現一個實質相同的「新 spec」，§9.3 要求的完整嘗試日誌從此失真（同一假設被記成多筆），且改動 payload 本身違反 §19-1 的「不改動程式」。

> 證據：internal/orchestrator/agent_prover.go:138 `seenHashes[specHash(spec)] = true; pendingSpec = spec`（核可即記，早於 Prove 執行）；agent_prover.go:403-406 duplicate 檢查無任何「env 失敗後豁免」條件；SPEC §9.1 表：env 意義為「build 失敗、依賴安裝失敗、映像檔問題、provider 不可用」，§19-1「不改動程式，修正環境後重跑」。

**建議修法**：把 seenHashes 的記錄點移到該 spec 的 run 結果落地之後（且僅對 harness／controlled_miss 結果記入，env 結果豁免重送）；或讓 orchestrator 在 env 失敗時以同一 pendingSpec 自動重跑（不回模型），使 §19-1 的「修正環境後重跑」不經過 submit 閘。

### F111 [P2] negative／positive 控制run 也落 witness_spec_submitted：一次模型提交在 journal 變三筆 spec 提交事件
SPEC：§21.3（witness_spec_submitted 語意）、§5.2｜維度：state-machine（R2）

runOne 對每個 kind（negative／positive／exploit）都先 clone spec、把 payload 覆寫成 pack 良性載荷或 exploit payload，再無條件 Append witness_spec_submitted。一次模型提交因此產生三筆「提交」事件，其中兩筆的 payload 根本不是模型提交的內容，且事件 payload 只記 template_id／oracle_id、不含 spec hash 與實際 payload——重放者既無法從 journal 重建 PrevSpecHashes（跨重啟 duplicate 偵測因此不可能），也會把每 finding 的 spec 歷史放大三倍。反例：journal 顯示 F-0007 有 9 筆 witness_spec_submitted，實際上模型只提交過 3 個假設。

> 證據：internal/orchestrator/prove.go:178-181 `spec := cloneSpec(in.Spec); spec["payload"] = payload`（negative/positive 用 benign），其後 prove.go:201-204 無條件對三個 kind 各 Append 一筆 {"witness_spec_submitted", run_id, kind, template_id, oracle_id}——事件欄位無 payload/spec_hash，無法與模型提交區分。

**建議修法**：witness_spec_submitted 只對模型提交的原始 spec 記一次（Prove 進入時，含 spec_hash 與 payload），negative/positive 的 payload 派生僅以 run_requested（已含 kind/nonce）表達；或至少在事件中加 spec_hash 與實際 payload 欄位並標記 derivation=benign/exploit。

### F112 [P2] budget_updated 是全工具唯一被吞錯的 Append：journal 靜默丟失預算狀態轉移
SPEC：§4（journal 記錄所有狀態轉移）、§9｜維度：state-machine（R2）

全工具對 journal.Append 的錯誤一律顯式上拋（main.go 各處、prove.go:209/487/492、agent_prover.go:380/418 都檢查），唯獨 journalBudget 寫成 `_, _ = p.Journal.Append(...)`。SQLite 寫入一旦失敗（磁碟滿、鎖逾時），budget_updated 事件靜默消失，而 in-memory 計數器繼續扣——journal 從此與實際預算狀態分歧，事後審查／重放看到的失敗分類序列不完整。§4 要求 journal 記錄「所有」狀態轉移；budget 扣抵正是 §9/§19 的核心狀態轉移。

> 證據：internal/orchestrator/prove.go:618 `_, _ = p.Journal.Append("budget_updated", findingID, map[string]any{...})`——對照同檔 209、487、492 行同為 Append 但皆 `if _, err := …; err != nil { return … }`。

**建議修法**：journalBudget 回傳 error 並由 runOne 上拋（與同檔其他 Append 一致，fail-closed），或在呼叫端檢查後 return err。

### F113 [P2] disposition 先寫 findings.json 再開 journal／append 事件：journal 失敗即檔案與 journal 永久分歧，且事件無讀回路徑
SPEC：§8（disposition 唯一寫入點）、§4（journal 記錄狀態轉移）｜維度：state-machine（R2）

report --set-disposition 的順序是：讀 findings.json → 改 disposition → WriteFindings 落檔（318）→ 之後才 journal.Open（322）與 Append(disposition_updated)（327-332）。journal.Open 可能因 schema_version 不符等理由失敗，此時 findings.json 已帶新 disposition 而 journal 無對應事件——journal 重放（§4 crash recovery 的唯一依據）會得到舊 disposition，雙源永久分歧。另外 318 與 333 對同一內容連寫兩次 findings.json（第一次在 journal 事件之前、第二次在之後），第二次失敗同樣造成「事件已記、檔案半新」的中間態；而全工具沒有任何路徑從 journal 讀回 disposition_updated，journal 事件對此狀態是純 write-only。

> 證據：cmd/aegis/main.go:318 `if _, err := reporting.WriteFindings(runDir, findings); err != nil { … }`（在 322 `journal.Open` 之前）；327-332 才 Append disposition_updated；333 第二次 `reporting.WriteFindings(runDir, findings)`；grep 證實 disposition_updated 僅此一處寫入、無任何讀取點。

**建議修法**：調整為 journal.Open → 逐筆 Append disposition_updated → 單次 WriteFindings（刪除 318 的提前寫回與 333 的重複寫回），使順序符合 §8「寫入 journal 後重新產生報告」且單一寫入點。
